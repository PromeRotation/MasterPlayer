### 3.1 原生迁移与统一寻路的衔接约定

2026-11-24 确认：原生脚本迁移继续推进；统一寻路模型的传送与固定跳点试点另行推进，不作为当前迁移的前置工作。本节约束新增及当前正在修改的实现，不表示统一转移 API 已存在，也不要求批量重写已有普通 AOE 或立即改造全部特殊移动。

**职责边界**

- 机制模型维护“发生什么”：事件驱动的状态、来源与目标身份/代际、位置/朝向锁定规则、准备/判定/结束时间，以及失效和撤销条件。BMR 源码作为语义对照，模型不重新消费 BMR 桥结果。
- 公共输出层维护“如何适配当前能力”：普通危险区、目标、障碍继续使用现有 MP 门面；地城优先沿用 `DungeonEncounter → DungeonOutput → SafeZone`，其他脚本复用各自已有公共输出层。几何投影、当前求解器数据转换与显示输出在此集中处理，避免副本模型依赖栅格索引、A*/SIPP 节点或调度器内部状态。
- 执行组件消费移动/交互/动作请求并确认开始、完成和失败，统一遵守移动总开关、owner、宿主控制权及回放隔离。机制模型和后台快照不直接调用原生操作；只在存在实际前后依赖时衔接交互、任务动作和移动。

**特殊移动与约束**

- 传送、跳跃、滑行、击退、拉近及强制行进保留明确类型和可查证参数。按当前机制实际需要保留入口/出口或位移规则、触发方式、可用/判定时间、耗时、方向、撞墙/落地规则、免疫条件及中断限制；未知项明确未知，不猜测。多层/跨场地机制保留已有的区域、支撑层或高度判据，不能仅因 X/Z 重合就合并空间。
- 机制模型中的原始信息不能只剩下危险区投影、落点箭头、硬编码最终坐标或一个暂停标志。当前危险区/安全区投影及专用控制可以继续作为适配实现，但要能追溯到原机制及其时序；不为地面搜索方便，将真实缺口无条件声明为可步行区域。
- “禁止移动”“必须持续移动”“到时发生强制位移”分别保留原因、生效窗口和结束条件；`Hints.SetMovementHold` 只承担当前执行策略，不能替代这些机制语义。强制位移不是可随意跳过的可选捷径。

- 特殊路线和原生操作通过明确的执行接入点消费；复用现有执行组件，将副本差异保留在参数及必要验证中。需要新接入时，集中处理门控、续期、完成/失败确认和 owner 撤销，避免在各副本复制搜索器、控制循环或直接操作 GreenMove/原生动作的衔接代码。确认实际起跳/落地等必要验证继续保留。

### 3.2 衔接边界的验收

- **机制模型**：验证事件、来源/目标代际、参数、判定时刻、取消与结束，避免测试只断言当前投影后的几个危险区。切人和反向 Seek 后仍能按同一机制重建。
